# 数据管线与城市迁移指南

> 本文记录「城市公共交通制霸」从 CPTOND 源数据到可玩游戏的完整处理流程、开发过程中踩过的数据/算法坑，以及把工作流快速迁移到新城市时的清单。
> 目标是：**换一个城市，只改「源数据路径 + 少量城市参数 + 少量数据修正」，其余全流程复用。**

---

## 一、整体流程总览

```
CPTOND 源数据（shapefile）
   │  ① 解析 SHP/DBF（lib/shp.js，零依赖）
   │  ② 线路↔站点按 route_cn 匹配
   │  ③ 同线路双向合并（去 "(起点--终点)" 后缀）
   │  ④ 逐站距离 d（km，到下一站）
   │  ⑤ 数据修正（幽灵站剔除等）
   │  ⑥ WGS-84 → GCJ-02（仅中国大陆需要）
   │  ⑦ 路径抽稀 + 复合站点 id
   ▼
data/beijing-transit.json（约 18.9MB）
   │  运行时加载
   ▼
shared/router.js buildGraph()                 → 物理站去重、逻辑站合并、寻路图
   ├── frontend/js/data/index-builder.js      → 适配前端索引与渲染
   └── backend / frontend                     → 共用 Dijkstra 与成本模型
```

关键文件：
- `cptond-convert.js`：一次性转换脚本（Node，离线运行）
- `lib/shp.js`：SHP/DBF 解析器（不依赖第三方库）
- `data/beijing-transit.json`：转换产物（被前端和寻路器共同读取）
- `frontend/js/app.js`：UI + 玩家侧计算
- `shared/router.js`：寻路引擎（浏览器/Node 通用）

## 二、源数据说明

- 来源：**CPTOND-2025**（Nature Scientific Data 发布，figshare 上可下载，全球多城市公共交通数据）。
- 结构：每个城市一个目录，含 `*_routes.shp`（线路几何）、`*_stops.shp`（站点）、`*_segments.*`（相邻站间段距）等。
- 坐标：原始为 **WGS-84**。中国大陆地图（高德）用 **GCJ-02** 火星坐标，必须转换，否则点位会偏移数百米。
- 数据量（北京）：约 2200 条公交线 + 35 条地铁线，约 5.7 万条「站-线」记录。

### 迁移注意
- 非中国大陆城市（或不用高德底图）：**跳过 GCJ-02 转换**，直接用 WGS-84。
- CPTOND 对不同国家/城市的结构基本一致，但字段可能有细微差异（`route_cn`、`type_en`、`s_stopid/e_stopid` 等），转换前先打印一两条记录核对。

## 三、转换脚本做了什么（cptond-convert.js）

1. **解析**：`parseShp` / `parseDbf` 读入线路与站点。
2. **匹配**：站点按 `route_cn` 挂到线路；全程用 `Map` 保证 O(N)（北京 bus_stops 约 11 万条，不能 O(N²)）。
3. **双向合并**：同一条线的两个方向按「去掉 `(起点--终点)` 后缀后的 base name」合并，只保留最优方向（几何点数多、站点多的）。
4. **逐站距离 d**：每个站存「到下一站」的公里数。优先用 CPTOND segments 真实值，缺失时用 haversine 兜底。末站 `d = null`。
   - 这是后面算乘车时间的核心输入（乘车时间 = 段距/速度 + 停站时间）。
5. **路径抽稀**：每条线几何抽稀到 ≤300 个点、坐标 6 位小数，控制 JSON 体积。
6. **复合站点 id**：见「坑 1」。
7. **数据修正**：见「坑 2」。

输出 JSON 结构：
```json
{
  "city": "北京",
  "source": "CPTOND-2025 (WGS-84 → GCJ-02)",
  "generated_at": "...",
  "count": 2213,
  "lines": [
    {
      "id": "L_xxxx", "name": "地铁1号线八通线", "mode": "metro",
      "front": "…", "terminal": "…",
      "stops": [ { "id": "BV…@lng,lat", "name": "…", "lng": …, "lat": …, "seq": …, "d": 1.2 } ],
      "path": [ [lng, lat], … ]
    }
  ]
}
```

## 四、踩过的坑（重要，迁移时务必对照）

### 坑 1：`临时站` 等占位站复用同一 stop_id
- **现象**：大兴 827 路和远在平谷的「平谷-三河」都有一个叫「临时站」的站，stop_id 都是 `BV09413140`，但坐标相隔 80 公里。按 id 去重后被当成同一个站，产生「虚空换乘」（一站从大兴跳到平谷）。
- **根因**：CPTOND 对「临时站」这类占位站，在多条线路上复用了同一个 BV id。
- **修复**：转换时把站点 id 改成 **`原始id@lng,lat`** 复合键，保证 `(id, 坐标)` 唯一。
  ```js
  const sid = s.id ? String(s.id) + '@' + lng.toFixed(5) + ',' + lat.toFixed(5) : null;
  ```
- **迁移注意**：任何城市都可能出现，**保留复合 id 逻辑**，不要回退成纯 BV id。

### 坑 2：幽灵站（未开通站）
- **现象**：北京地铁 14 号线的「高家园」站实际未开通，但数据里有。
- **修复**：在转换脚本里显式剔除（按线路名 + 站名）：
  ```js
  if (base === '地铁14号线') {
    const g = stops.findIndex((s) => (s.name || '').includes('高家园'));
    if (g >= 0) stops.splice(g, 1);
  }
  ```
  剔除后，前一个站的 `d` 会自动按「前一站 → 下一站」重算（haversine 兜底）。
- **迁移注意**：新城市大概率也有类似未开通/预留站，需要**人工核对**。建议转换后按「线路首末站 + 站数」抽查，或用地图对比。

### 坑 3：并查集合并的「传递性」导致同线两站被并进一个逻辑站
- **现象**：规划耗时和最优路线明明一样却差 2 分钟。排查发现「单店北站」「单店东」都在 96 路上（本不该合并），却通过桥接站「单店」被传递合并进同一逻辑站，96 路在这个逻辑站里有两个物理站，`stopByLine` 只留一个，寻路就「跳过」了一站、少算了时间。
- **根因**：合并用了并查集（union-find），`!sharesLine` 只阻止「直接」合并，挡不住「A↔B 经 C 桥接」的传递合并。
- **修复**：给每个簇维护一个 `rootLines`（该簇所有线路集合），合并前检查两簇线路集合是否有交集，有交集就拒绝合并：
  ```js
  const la = rootLines.get(ra), lb = rootLines.get(rb);
  for (const lid of la) if (lb.has(lid)) return; // 同线两站不合并（含传递）
  ```
- **迁移注意**：这是最容易复发的坑。**合并逻辑必须同时满足：距离 + 站名匹配 + 不共线（含传递）**。该逻辑现在只在 `shared/router.js` 中维护，前端索引直接消费其建图结果。

### 坑 4：机场航站楼站名不统一
- **现象**：首都机场 T2 有「T2航站楼 / 2号航站楼 / 2号航楼 / 首都机场T2航站楼」等 6 种叫法，大兴机场有「大兴机场 / 航站楼 / 航站楼(…方向)」等，互相不匹配，无法换乘。
- **修复**：增加 `airportTerminalMatch()`，把站名归一化到 `t2 / t3 / daxing` 三个 key，视为同名（距离校验仍保留）：
  ```js
  function airportTerminalKey(name) {
    if (name.includes('大兴机场') || /^航站楼/.test(name)) return 'daxing';
    const isCapital = name.includes('首都机场') || /^T[23]/.test(name) || /^\d号航/.test(name);
    if (!isCapital) return null;
    if (/2/.test(name) && !/3/.test(name)) return 't2';
    if (/3/.test(name) && !/2/.test(name)) return 't3';
    return null;
  }
  ```
- **迁移注意**：机场/火车站这类枢纽是重灾区。新城市上线前，先对枢纽站（机场、火车站）的站名做一次聚类核对，补对应的特殊匹配规则。

### 坑 5：地铁环线被拆成两条线性线，首尾不闭环
- **现象**：北京 2 号线/10 号线在数据里是「内环」「外环」两条线，但每条都是**线性数组**，首尾站（如积水潭↔西直门）之间的闭环段缺失，导致环线只能走长的那一边。
- **修复**：
  1. 检测环线（线路名含「内环/外环」），算出首尾站的闭环距离 `wrapDistKm`。
  2. Dijkstra 给环线补首尾闭环边（走站少的那边）。
  3. `rideStatsBetween` / `rideStats` 同时算「线性」与「绕环」两个方向，取时间少的那边。
  4. `lineSegmentPath` 绘制时，闭合路径上选较短的那条弧。
- **迁移注意**：有环线（loop）的城市（如北京 2/10 号线、上海 4 号线、成都 7 号线）必须处理。检测方式建议：线路名含「内环/外环」或首尾站地理相邻。

### 坑 6：换乘站（多物理点合并成一站）起终点的上下车点选错
- **现象**：终点是动物园（多物理站合并成的逻辑站），最优路线从 4 号线下车，但答案却按「离终点直线最近」的 16 号线动物园站算步行，起点同理。
- **根因**：候选站是「离起/终点直线最近」的物理站，但真正上下车的物理站是「所选线路上的那一个」。
- **修复**：寻路结果算完后，做一次后校正——用 `physicalStopFor(逻辑站, 线路)` 取所选线路上的物理站，重算上下车步行：
  ```js
  const alightPhys2 = physicalStopFor(graph, best.bestState.logicalId, best.bestState.lineId);
  ```
- **迁移注意**：任何「同名多物理点合并」的站都会有此问题，跟坑 3、坑 4 联动。

### 坑 7：步行策略的演进
- 最初用高德 Walking API 算步行时间/路径。
- 后来发现没必要，统一改成**直线距离 / 75 m/min**（`straightLineWalk`），并把候选站限制在 1.5km 内（`MAX_WALK_KM = 1.5`）。
- 随机模式的起终点偏移也限制在 1.5km 内（`RANDOM_OFFSET_MAX_M = 1500`）。
- **迁移注意**：如果新城市想更真实，可重新接入步行导航 API，但要保证玩家侧和最优答案侧用同一套步行逻辑（否则会出现「一模一样却差时间」的 bug）。

### 坑 8：玩家路线 vs 最优路线耗时不一致
- 表面是「一样的路线差几分钟」，根因其实是坑 3（传递合并跳站）导致的 Dijkstra 实际边数与展示重构不一致。修好坑 3 后自动消失。
- **迁移注意**：**玩家侧和最优侧的「段距、停站、等车、换乘」参数必须完全一致**。前端计时现在直接复用 `shared/router.js` 的参数和乘车统计，不再维护第二套公式。

### 坑 9：逻辑站 id 碰撞（导致「玩家比系统最优还快」）
- **现象**：最优路线明明应该更快，玩家却规划出了比它还快的路线。排查发现某逻辑站（马连店）本应经过 15 条线路，`logicalById` 里却只剩 1 条——最优路线在该站被「切断」，只能绕远路。
- **根因**：逻辑站 id 最初用 `'S_'+站名+'@'+lng,lat(4位小数)` 生成。对「同名且坐标相近、但因共享线路而无法合并」的多个簇（比如同一条公交线上的同名站），这个 id 会**完全相同**，`logicalById.set(id, ...)` 后写覆盖先写，导致前面簇的线路信息全部丢失。
- **修复**：id 追加物理站代表点的 `'#'+rep.id`，保证全局唯一：
  ```js
  const id = 'S_' + name + '@' + rep.lng.toFixed(4) + ',' + rep.lat.toFixed(4) + '#' + rep.id;
  ```
  逻辑站 id 只在 `shared/router.js` 的 `buildGraph` 中生成；前端索引直接适配同一份结果。
- **迁移注意**：这是「同名站合并」逻辑的隐性坑，任何有同名公交站的城市都会触发。上线新城市前，跑一遍 test-optimal-invariant.js（会穷举 0/1 次换乘验证「系统最优始终 ≤ 玩家」），若出现「最优被玩家击败」就说明有 id 碰撞或合并错误。

## 五、运行时数据处理（共享建图 + 前端适配）

`shared/router.js` 是站点合并和线路派生字段的唯一实现，`frontend/js/data/index-builder.js` 只把建图结果适配进前端状态：

1. **物理站去重**：按复合 id `原始id@lng,lat` 去重（对应坑 1）。
2. **逻辑站合并**：
   - 空间网格（CELL=0.01）+ 并查集。
   - 合并条件：`距离 < 300m` 且（`namesMatch` 或 `airportTerminalMatch`）且 `!sharesLine`。
   - 传递安全：`rootLines` 防同线两站合并（对应坑 3）。
   - 每个逻辑站保留 `stopByLine[线路id] = 物理站id`，这是「某条线在该站真实经过的物理点」的唯一来源。
3. **公交速度模型**：按线路平均站间距动态给巡航速度（城区密站慢 / 郊区大站快）：
   ```js
   busVmax = LOCAL(16) + (EXPRESS(36.45) - LOCAL) * clamp((avgSpacing - 0.5) / (2.0 - 0.5), 0, 1)
   ```
4. **环线检测**：`isLoop` + `wrapDistKm`（对应坑 5）。

## 六、寻路与成本模型（shared/router.js）

- **算法**：在 `(逻辑站, 线路)` 状态空间上做 Dijkstra。
- **边**：
  - 乘车边：`段距/速度 × 60 + 停站时间`（地铁匀速，公交梯形加速 0→a→vmax→匀速）。
  - 换乘边：`换乘惩罚 + 等车时间`。
- **候选站**：起/终点各取直线最近且 ≤1.5km 的 3 个公交站 + 2 个地铁站。
- **情景模式**：`noMetro`（禁地铁）、`busSpeedFactor`（公交速度系数）、`walkSpeedFactor`（步行速度系数）。

### 当前成本参数（迁移新城市时重点校准）
| 参数 | 值 |
|---|---|
| 地铁巡航速度 | 35 km/h |
| 地铁停站 | 0.6 min |
| 公交停站 | 0.4 min |
| 公交加速度 | 0.3 m/s² |
| 公交快车最高速 | 36.45 km/h |
| 公交慢车最高速 | 16 km/h |
| 慢车/快车站间距分界 | 0.5 km / 2.0 km |
| 地铁等车 | 2.5 min |
| 公交等车 | 5 min |
| 地铁↔地铁换乘 | 3 min |
| 公交↔公交换乘 | 0 min |
| 公交↔地铁换乘 | 5 min |
| 同名站合并距离 | 300 m |
| 起终点步行上限 | 1.5 km |
| 步行速度 | 75 m/min |

## 七、迁移到新城市的步骤清单

1. **准备源数据**：下载该城市 CPTOND 的 `*_routes.shp`、`*_stops.shp`、`*_segments.*`，放到对应目录。
2. **改转换脚本**：
   - 改输入/输出路径。
   - 确认字段名（`route_cn`、`type_en`、`s_stopid/e_stopid`）。
   - 中国大陆 → 保留 GCJ-02 转换；非中国 → 去掉（直接用 WGS-84）。
   - 加城市数据修正（幽灵站剔除、枢纽站名特判，见坑 2、坑 4）。
3. **跑转换**：`node cptond-convert.js`，生成 `data/<城市>-transit.json`。
4. **改前端加载**：`DATA_FULL` 指向新城市 JSON；地图中心点 `MAP_CENTER` 改成新城市。
5. **核对数据**（强烈建议）：
   - 抽查几条线：首末站、站数、站间距是否合理。
   - 枢纽站（机场/火车站）站名聚类是否已合并（坑 4）。
   - 是否有环线，环线闭环是否正确（坑 5）。
6. **校准成本参数**：第六节的表（地铁/公交速度、等车、换乘、合并距离、步行上限）。
7. **回归测试**：`node test/test-router.js` 跑通；浏览器里规划一两条路线对比现实直觉。
8. **关卡/剧情文案**：替换 `LEVELS` 数组里的城市相关地名和剧情。

## 八、需要「城市化」的散落常量/位置（速查）

> 2026 重构后：城市列表、地图中心、数据文件路径、故事模式开关都集中到 `frontend/js/data/cities.js` 一份清单，
> `cptond-convert.js` 也有 `CITIES` 表，加新城市只需两处各加一行 + 下载源数据。

| 位置 | 内容 |
|---|---|
| `frontend/js/data/cities.js` | 城市清单：id / 中文名 / 地图中心 / 是否有故事模式 / 兜底数据 |
| `cptond-convert.js` `CITIES` | 源数据目录 + 中文名（与 cities.js 的 id 对应） |
| `cptond-convert.js` `GHOST_STOPS` | 各城市幽灵站修正（坑2） |
| `frontend/js/data/levels.js` `LEVELS` | 故事模式关卡（起终点、地名、剧情）——目前仅北京有 |
| `shared/router.js` `DEFAULT_PARAMS` | 速度/停站/等车/换乘、同名站合并距离、起终点步行上限（前端自动复用） |
| `shared/router.js` `airportTerminalKey` | 枢纽站名归一化规则 |
| `frontend/js/core/config.js` `WALK_TRANSFER_MAX_M` | 玩家手动步行换乘上限 |

## 九、快速上手的建议顺序

1. 先照搬北京这套，跑通一个「只有几条线」的最小城市，验证管线。
2. 再上完整城市，重点做「数据核对」（坑 2、3、4、5 都会在真实数据里出现）。
3. 最后校准成本参数（第六节）。
