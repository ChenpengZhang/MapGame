# 城市交通线路规划游戏 — 技术方案 v0.5

> 状态：MVP 已实现（单机闭环跑通），进入打磨与联网演进阶段
> 更新：数据/坐标/渲染架构在实现中重新决策并固化（见 §2 标注）

---

## 1. 项目概述

**核心玩法**：给定城市中两个地点 A、B，玩家在多模式公共交通网络（地铁 + 公交）中规划最快换乘组合；系统用本地图寻路给出"理论最优时间"作为基准，按玩家方案与基准的差距计分。

**一句话定位**：*GeoGuessr × 公共交通——猜一猜，从 A 到 B，最快到底要多久？*

**当前已实现的游戏形态**（单机，Web）：

| 模式 | 说明 |
|---|---|
| 故事模式 | 6 个关卡（漫漫上学路/汽车不可到达之地/机场到机场/瘫痪的地铁/一路畅通/大雨滂沱），带 Galgame 对话 + 教学气泡，逐关解锁；部分关卡自带情景 |
| 自由模式 | 随机起终点，二级菜单用**按钮**选择情景（禁地铁/公交加速/大雨），成绩不落盘 |
| 无尽模式（爬塔） | 随机起终点，4 个畸变按钮（普通/地铁瘫痪/一路畅通/大雨）分别记录成绩；每层要求比最快慢 ≤ 固定百分比，从 100% 逐层收紧到 1%（约 12 层后封顶 1%）；支持中途退出续玩 + 「从第1层重来」 |
| 排位模式 | **占位**（未来在线 1v1，见 §11） |

## 2. 已确认的决策（含实现期修正）

| 决策项 | 结论 | 状态 |
|---|---|---|
| 首发城市 | **北京** | 已定 |
| 游戏形态 | **先单机，后期联网** | 单机已实现 |
| "最优时间"基准 | **本地图寻路**（Dijkstra over `(逻辑站, 线路)`），支持情景模式 | ✅ 已实现 |
| 数据来源 | **CPTOND-2025 开源数据集**（figshare，WGS-84），高德接口仅作备选爬虫 | ✅ 已实现 |
| 坐标系 | **全项目唯一一份 GCJ-02 数据**；高德底图直接用，OSM 底图在渲染边界（polyfill）统一 GCJ-02→WGS-84 | ✅ 已实现（实现期修正，见下） |
| 步行段 | **直线距离 / 75 m·min⁻¹**，不再调高德步行导航（零 API、可离线） | ✅ 已实现（实现期修正） |
| 玩家路线时间 | **本地成本模型**（与基准同源）：乘车=段距/速度+停站+加速、等车、换乘惩罚 | ✅ 已实现 |
| 地图底图 | **双后端**：默认 Leaflet+OSM（免 Key），设置里填高德 Key 则自动切高德 | ✅ 已实现 |
| 高德 Key | 只存浏览器 localStorage（`mg_amap_key`/`mg_amap_security`），**不进代码/仓库**；设置页附获取教程链接 | ✅ 已实现 |
| 道路等级估速 | **已删除**：不做 OSM 地图匹配，规避 map-matching 风险 | 已定 |
| 参数校准 | **待做**：离线标定（分层样本 + 双目标 Loss + Nelder-Mead/Optuna），运行时零高德调用 | 计划中 |

> **实现期关键修正 ①（坐标系）**：最初设想"两套数据来回切换"（GCJ-02 版 + WGS-84 版）。
> 实测发现路由对坐标敏感——站点合并（300m 阈值）、候选站排序、步行距离都会在阈值附近
> 因两套坐标的亚米级差异而翻转，导致**两端最优路线不一致**（逻辑站数 14789 vs 14787）。
> 最终改为**单一 GCJ-02 数据源**，OSM 的坐标换算全部收进 `frontend/js/amap-polyfill.js` 渲染边界，
> app.js 无感知、高德路径零改动。这样两端路由、点位、交互天然一致，内存也只需一份（约 87MB）。
>
> **实现期关键修正 ②（步行）**：步行不再调高德导航，改为直线距离 / 75 m·min⁻¹（受情景 `walkSpeedFactor` 影响）。
> 起终点步行上限 1.5km，超过则提示就近选站。收益：零 API 调用、无 key 也能完整玩、可完全离线。

## 3. 总体架构（单机已实现，预留联网）

```
┌─────────────────────────────────────────────────────────┐
│  数据采集层（开发期/运维期）                                │
│  CPTOND-2025 shapefile（WGS-84）→ cptond-convert.js       │
│  （自研零依赖 SHP/DBF 解析 lib/shp.js）→ 合并/去重/抽稀/GCJ │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  数据产物（开发期打包进仓库）                               │
│  data/beijing-transit.json（18.9MB，2213 线 / 5.7 万站记录）│
│  data/sample.json（6 线演示兜底）                          │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  单机客户端（浏览器，node server.js 静态服务）              │
│  ┌────────────┐ ┌──────────────┐ ┌───────────────────┐  │
│  │ 本地数据包  │ │ 本地寻路器    │ │ 渲染层            │  │
│  │ lines/stops │ │ router.js    │ │ 双后端 AMap 抽象  │  │
│  │ 关卡/爬塔   │ │ Dijkstra     │ │ (高德/Leaflet)    │  │
│  └────────────┘ └──────────────┘ └───────────────────┘  │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  联网服务端（已接入账户/权威结算/排行榜/每日挑战）       │
└─────────────────────────────────────────────────────────┘
```

### 3.1 联网模式的数据表

```text
user
  └─ game_runs                  共用的一次游戏生命周期
       ├─ run_rounds             该局的第 N 轮题目
       │    └─ round_submissions 这一轮的提交与结算
       ├─ timed_run_results      每日/随机/故事的单次用时结果
       └─ tower_run_stats        无尽模式的层数与累计用时

daily_challenges
  └─ game_runs                  通过 daily_challenge_id 关联当日题目
```

- `game_runs` 只保存各模式都一样的属性：玩家、模式、城市、场景、数据版本、规则版本、状态和开始/结束时间。`mode` 明确区分 `tower` / `daily` / `free` / `story`。
- 每日挑战是独立模式：题目定义在 `daily_challenges`，成绩在 `timed_run_results`。它仅复用通用的游戏局生命周期，不与无尽成绩混存。
- 无尽模式的结果单独放在 `tower_run_stats`：`cleared_layers` 是通过层数，`total_elapsed_ms` 是已通过各层的实际游玩时间总和。排行先按层数降序，层数相同时按累计实际用时升序；随机题目的路线模拟耗时 `duration_ms` 不用于同层排名。前端展示前 20 名，榜外登录玩家另显示本人名次。
- 原 `run_stages` / `run_submissions` 已改名为 `run_rounds` / `round_submissions`。这里表达的是一局内的第 N 轮，不再与“无尽层数”或“故事关卡”混用。
- 不按模式复制四套完整表：用户归属、并发提交、版本校验和局状态的规则相同，复制后反而容易产生四份不一致逻辑；只将真正不同的结果拆表。

**关键设计**：路线数据和寻路仍可本地运行；联网模式由服务端权威出题与结算，高德 Key 不暴露给客户端。

## 4. 数据层

### 4.1 数据源（已实现）

- **主数据源：CPTOND-2025**（[figshare](https://figshare.com/articles/dataset/CPTOND-2025/29377427)，WGS-84，含北京公交+地铁的 routes/stops/segments）
- **备选：高德公交信息查询 API**（`frontend/js/fetch-data.js` 爬虫，基本不用），仅作为 CPTOND 缺数据时兜底
- **自研解析**：`lib/shp.js`（零依赖 SHP/DBF 读取器），`cptond-convert.js` 生成最终 JSON

### 4.2 数据模型（实际产出 `beijing-transit.json`）

```jsonc
{
  "city": "北京", "count": 2213,
  "lines": [{
    "id": "L_xxx",            // md5(线路名) 前缀，稳定
    "name": "地铁2号线外环", "mode": "metro|bus",
    "front": "西直门", "terminal": "积水潭",
    "start_time": "05:10", "end_time": "23:30",
    "stops": [{ "id": "BV…@lng,lat", "name": "西直门", "lng": 116.35, "lat": 39.94, "seq": 1, "d": 1.2 }],
    "path": [[116.35, 39.94], …]   // 抽稀后轨迹，GCJ-02
  }]
}
```

- `d`：该站到下一站的公里数（末站 `null`），优先用 CPTOND segments 真实距离，缺失用 haversine 兜底
- 站点 `id` = `原始id@lng,lat` 复合键，避免 CPTOND「临时站」复用同一 stop_id 导致"虚空换乘"
- 坐标全为 **GCJ-02**（数据源 WGS-84 在转换脚本里统一转换）

### 4.3 ETL 要点（已实现，见 `docs/数据管线与城市迁移指南.md`）

1. 线路↔站点靠 `route_cn` 精确匹配，O(N) 建索引
2. 同一线路两个方向按 `route_cn` 去后缀合并为一条
3. 轨迹抽稀到每线 ≤300 点、坐标取 6 位小数，控制体积（18.9MB）
4. 幽灵站剔除（如 14 号线「高家园」未开通）
5. 环线（内环/外环）补闭环距离，供"走站少的那边"

### 4.4 数据量（北京，实际）

| 项目 | 量级 |
|---|---|
| 线路 | 2213 条（地铁 35 / 公交 2178） |
| 站记录 | 57122 条（物理站 29013 / 逻辑站 14789） |
| 轨迹点 | 56.7 万（抽稀后） |
| 数据文件 | 18.9MB（解析后内存约 87MB：文本 37MB + 对象 51MB） |

结论：本地存储/内存无压力。

## 5. 基准层（本地寻路，已实现）

### 5.1 候选站点集

- 对每个起终点，本地取 **1.5km 内的全部公交与地铁站** 作为候选步行站
- 问题退化为：在候选上车站 × 候选下车站的组合中，求最优换乘路径 + 两端步行，取最小

### 5.2 图模型（状态 = 逻辑站 × 线路）

- **节点**：状态 `(stop, line)` —— 表示"刚到站点 `stop`，当前所乘线路为 `line`"
- **边**：
  - **乘车边**：沿同一 `line` 相邻站 a→b，权重 = 段距/速度 + 停站 + 加速损耗
  - **换乘边**：同一逻辑站内 `line₁ → line₂`，权重 = 换乘惩罚(mode₁,mode₂) + 等车(line₂)
- 复杂度：状态数 ≈ 线路×站点出现次数，堆优化 Dijkstra **毫秒级**（实测寻路 470ms 含建图 390ms）

### 5.3 关键实现细节

- **换乘站合并**：距离 <300m 且站名匹配（相同或互相包含）的物理站合并为逻辑站，公交↔地铁换乘打通
  - 机场航站楼特殊匹配（T2航站楼↔2号航站楼、大兴机场↔航站楼）
  - **传递合并防护**：并查集每簇记录线路集合，若两簇共享同一线路则不合并（避免把同线两个站合并成"自己换乘自己"）
- **环线**：内环/外环首尾相邻补闭环边，`rideStatsBetween` 双向取时间少的那边
- **换乘站上下车点修正**：候选站是"离起/终点最近的那个物理站"，但换乘站按所选线路取准确物理站（`physicalStopFor`），上下车步行时间按它重算

### 5.4 特殊情景模式

| 模式 | 实现方式 |
|---|---|
| 禁用地铁 | 可用线路集合剔除地铁 |
| 公交加速/减缓 | `busSpeedFactor`（1.2=加速20%，0.5=减缓50%） |
| 步行减缓 | `walkSpeedFactor`（大雨 0.5） |

同一套 Dijkstra，仅替换"可用线路集合 / 成本参数"。

## 6. 渲染层（双后端，已实现）

### 6.1 后端抽象

- **统一 API 面**：`AMap.*`（`Map/Polyline/Circle/Marker/MassMarks`）
- **高德后端**：真实高德 JS API 2.0，`window.AMap` 原生
- **OSM 后端**：`frontend/js/amap-polyfill.js` 用 Leaflet 模拟同一 API 面，**唯一**知道 OSM 用 WGS-84 的地方

### 6.2 坐标换算（收口在 polyfill，app.js 无感知）

- 入口（app.js → Leaflet）：`Map center / setZoomAndCenter / setBounds / Polyline path / Circle center / Marker position / MassMarks lnglat` 统一 GCJ-02→WGS-84
- 出口（Leaflet → app.js）：`getCenter / getBounds` 统一 WGS-84→GCJ-02
- 标准迭代逆变换（GCJ-02→WGS-84），误差 <1 米，渲染够用
- **高德后端零换算、零改动**

### 6.3 渲染性能（已实现）

- 站点按视野渲染（外扩 35% 边距），公交站 zoom≥15、地铁站 zoom≥13 才显示
- 公交站超 8000 点时空间抽稀
- MassMarks 海量点：OSM 后端每站两层（小视觉点非交互 + 9px 透明命中圆交互），解决悬浮/点击精度问题
- 淡入/淡出非线性动画；路线悬浮置顶

### 6.4 交互需求（已实现）

- 起终点图钉、沿途站点点击换乘、终点点击完成
- 悬浮站点显示换乘信息卡（线路标签）
- 玩家方案路线动画 + 最优路线动画 + 分项时间对比

## 7. 本地成本模型（基准与玩家同源，已实现）

**设计原则：基准与玩家用同一套成本模型，保证公平可比较。**

1. **步行段（本地直线）**：`直线距离 / (75·walkSpeedFactor)`
2. **乘车段（本地）**：
   - 地铁：`段距 / 35 km/h + 停站 0.6min`
   - 公交：梯形加速模型（0→缓加速→线路最高速→匀速，加速度 0.3 m/s²）；**线路最高速按平均站间距动态取**（≤0.5km 密站慢车 16 km/h → ≥2.0km 郊区快车 36.45 km/h），再乘 `busSpeedFactor`
3. **等车（本地常量）**：地铁 2.5min、公交 5min
4. **换乘惩罚（按模式）**：公交↔公交=0、地铁↔地铁=3min、公交↔地铁=5min

**基准与玩家都用这套模型**，且都受情景参数影响。

**计分**（`gapRatio = 玩家耗时/最优耗时 - 1`）：

| 差距 | 评级 |
|---|---|
| ≤5% | 完美 ⭐⭐⭐ |
| ≤15% | 优秀 ⭐⭐ |
| ≤30% | 良好 ⭐ |
| >30% | 还有差距 |

**已知偏差与兜底**：本地模型绝对时间有偏差 → 区间计分吸收；结算时玩家路线与最优路线同时动画展示（教学）。

## 8. 参数校准（离线标定，计划中）

**定位**：成本模型的速度/停站/等车/换乘惩罚是初值，需离线用真实最优标定一次。

**目标函数**：
```
Loss(θ) = α · MAPE(本地最优时间, 真实最优时间)
        + β · (1 − 路线结构重合率)
```

**参数清单 θ**：地铁/公交速度、停站、等车、换乘惩罚、公交加速曲线、站间距分段阈值。

**优化算法**：Nelder-Mead / COBYLA（无梯度）；备选 Optuna 贝叶斯。目标含 argmin 不光滑，不能用梯度法。

**样本设计**：分层抽样（地铁主导/公交主导/混合 × 短/中/长距离）300–500 对，留 20% 验证。

**验收线**：中位时间误差 <10–15%，路线重合率 >70%。

> 注：当前步行已用直线估计，若后续要更准，可把"步行段"也纳入标定（用真实步行时间当老师），
> 但仍不改变"运行时零 API 调用"的原则。

## 9. 题库生成（已实现：关卡 + 随机）

- **故事关卡**：6 个手写关卡（坐标/时间上限人工调过，如机场 200min、地铁瘫痪 250min）
- **自由/爬塔随机题**：采样真实站点 + 随机偏移（300m–1500m，保证步行可控），迭代重抽保证两点 ≥3km
- **无尽爬塔难度**：`towerThreshold(layer) = layer≤1 ? 100% : max(1%, 100%-(layer-1)·99%/11)`，即第 1 层放宽到 2 倍最优，线性收紧到约第 12 层 1%，之后封顶 1%
- 后续：批量预生成 + 每日一题（Wordle 模式）

## 11. 联网演进路线

1. **M0 单机**：✅ 已实现（数据 + 关卡 + 三种模式闭环）
2. **M1 排位模式（重点）**：在线 1v1 匹配，GeoGuessr 式"一人答完后另一人 30 秒作答"，匹配系统 + 天梯积分
